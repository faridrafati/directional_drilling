# What to Build Next in WellView Online

**Source:** 161 claims adversarially re-checked across 14 sections of Peloton's own decoded user guide. 129 confirmed, 5 deliberate, 27 dismissed. Deduplicated below to ~80 distinct issues in five tiers.

**Line numbers were accurate when this was written** and have drifted since, as the fixes below landed. Treat them as a starting point, not a citation — the Status ledger under this section records what is closed.

---

## The honest shape of the result

129 confirmed findings sounds like a failing product. It is not what the numbers mean. This was an adversarial hunt through fourteen chapters of a 330-topic vendor specification, run by auditors instructed to find divergence. The count measures the search, not the app.

**What the app gets right does not appear in this list and is the larger part of it:** 357 tables converted and browsable, 182 of 213 report templates rendering against live data, the unit system driven by Peloton's own unit table, the reference datum, 5,761 field labels and help strings taken from the vendor's model rather than invented, CRUD with carry-forward and 22 shipped pick-lists, the schematic's nine layers, the query builder, export/import, the audit rules, days-vs-depth, wellheads, attachments, multi-well reports and the Excel extract. No auditor found a table the app cannot read or a shipped report it renders as garbage.

**The genuinely dangerous set is small — about twenty items, Tiers 0 and 1.** Everything from Tier 2 down is missing surface area: real, specified in the guide, wanted by a user, but nothing there tells anyone something false.

And those twenty concentrate into two habits, not twenty independent bugs:

1. **A value shown without the qualifier that gives it meaning** — a depth with no datum code, a criterion with no unit, 500 rows reported as "629 records", a filtered report that silently dropped its filter.
2. **A drawing made from a subset of the data that decides its shape** — string tops, cement type, lateral position.

Fix those two habits and the app is faithful nearly everywhere it matters.

# TIER 0 — Silent wrongness in stored data

These write into the same SQLite files the desktop reads. They are first because nothing else on this list survives a corrupted database.

### 0.1 Carry-forward writes a link GUID and drops its TK companion

- **Guide/model:** The app's own contract, `EditData.tsx:28-30`: "choosing one writes the GUID and keeps the …TK companion (the target table name) in step, exactly as the desktop stores it."
- **Now:** `EditData.tsx:515` — `if (!c.carryForward || c.tk || c.id || c.system) continue;` skips every TK column. `wellviewDb.ts:959` is what marks them. `datamodel.json` declares **zero** fields matching `/^idrec.+tk$/`, so no TK column can carry `carryForward` either — the block is doubled. `wellviewDb.ts:1216-1227` guards the DefaultWellboreLinker on `!values[wbCol]`, so a carried `IDRecWellBore` also suppresses the TK write.
- **Scope:** 52 model fields are `carryForward` + `foreignidrec` — `wvperforation.idrecstring`, `wvannularfluid.idrecstring`, `wvstimtreatstg.idrecfluid`, `wvproblem.idreczone`, `wvtestsssv.idrectubcomp` among them.
- **User cannot:** trust any record created by carry-forward to resolve its own link. The app's own derivations already depend on the TK — `calcDerivations.ts` records "34 wvProblem rows with resolvable TK (of 42 total)". Rows written by this app become the ones that will not resolve, in the app and in the desktop.
- **Size: small** (half a day) — carry the TK alongside the GUID in `carrySeed`. Plus a one-off backfill for rows already written.

### 0.2 A new record is written with no `sysSeq`, so it lands at the top of the folder

- **Now:** `wellviewDb.ts:1188-1196` filters every sys column out of the client's values, and the whole insert body (1180-1261) never touches `sysseq`. Contrast the paste route at 1114-1126, which reads `MAX(sysSeq)` for the scope and assigns `++seq`. `orderColumn` (411-418) prefers `sysSeq` for a sequenced table; the records query orders ASC; SQLite sorts NULL first.
- **Verified:** zero null `sysSeq` today across `wvCasComp` 215 / `wvCasCompTally` 776 / `wvTubComp` 528 — so every row this app writes becomes the first NULL in its folder.
- **User cannot:** add a joint to the bottom of a casing tally. It appears at the top, and the string's depth order is wrong from that moment onward, everywhere.
- **Size: small.** Note this also inverts the "no Insert Records" finding — the walk is *down*, not up.

### 0.3 The Equipment Type list writes the caption where WellView stores a table name

- **Guide:** `subject-areas-casing-cement-and-wellheads.txt:41`; same mechanism in `tubing-rods-and-other-equipment.txt:34/99/125` and `surface-equipment:35/54`.
- **Model:** `wvTubComp.CompSubTyp` is `lookuptyp="mdllistwithtables"` with an `idrectable` on ESP Intake/Motor/Pump, Gravel Pack, Mandrel, Packer, PCP Stator, Sensor, SSSV. `scripts/wellview-db/build_datamodel.mjs:214-238` keeps only `a.listitem` and drops `idrectable` — 1,144 occurrences in the model, **0 anywhere in the repo**.
- **The data settles it:** every entry that owns an `idrectable` is stored as the table name (`wvtubcomppacker` ×27, `wvtubcompmandrel` ×18, `wvtubcompsssv` ×10, `wvcascomplnrhngr` ×5 …), while every entry without one is stored as its caption (`Tubing` ×147, `Nipple` ×46, `Casing` ×121).
- **Now:** `EditData.tsx:1039-1045` and `:1064-1073` offer `modelList` as "Approved values, from WellView's own data model", store the picked string verbatim, and render the stored value verbatim.
- **User cannot:** read the type of 123 existing rows, which show `wvtubcomppacker` where the desktop shows `Packer`. And picking "Packer" writes the literal word, which the desktop will not map back to the detail table. Same defect on `wvWellHeader.LegalSurveyTyp` (two sample wells store `wvloccarter` / `wvlocoffshore`).
- **Size: medium** — re-export `idrectable` in `build_datamodel.mjs`, then a display/write mapping in the modelList editor. This one fix also unlocks 2.5 and the type-driven-subfolder item.

### 0.4 Inventory Transfer never writes the returned record on the source well

- **Guide:** `explorer-using-add-ins.txt`, Transferring Inventory (final line).
- **Now:** `inventory.ts:136-181` is the whole write path; the only two INSERTs (`:157`, `:167`) are bound to `opts.toWell`. `closingInventory()` (`:72-88`) sums received − returned − consumed `WHERE p.idwell = ?`, so the source balance never moves. `grep -rn "Returned" apps/api/src` finds no writer anywhere. The file header (`:22-25`) states what is written but gives no reason for omitting the source row; `inventory.test.ts` covers only the negative-balance rule and rollback.
- **User cannot:** rely on any source well's mud inventory. The same stock can be transferred off the same well repeatedly, and the source is overstated by every transfer ever made.
- **Size: small** — one INSERT and a test, but it is a two-sided transaction, so the rollback path needs exercising.

### 0.5 Deleting a record checks nothing that points at it, and cannot be undone

- **Guide:** `edit-data-working-with-records.txt` — 1.155 Deleting Associated Records ("A warning message lists the subfolders that are affected"), 1.162 Undoing Changes (which explicitly covers "deleting a record").
- **Now:** `deleteRecord` (`wellviewDb.ts:434-452`) recurses over prefix-children and DELETEs; the route (`:1362-1374`) does no reference check. `isLinkCol` (`:215-220`) already classifies `foreignidrec` columns and is not on the delete path. Undo All (`EditData.tsx:1176-1181`) is `setEdits({})` and nothing else; `remove()` (`:794-812`) calls the server immediately. The warning at `:798` is a fixed string naming nothing; the affected count arrives at `:803-806`, *after* the row is gone — while `deleteRecord` already walks exactly the tables that would need naming and `buildTree` (`:377-386`) already computes per-table counts.
- **Verified:** 34 `wvPerforation` rows join a live `wvZone` on `IDRecZone`; deleting that zone leaves 34 dangling GUIDs and `captionOfLink` (`EditData.tsx:663-671`) then returns null. One confirmed delete on a casing string destroys 222 tally rows with no way back.
- **User cannot:** recover from a misclick, or see what a delete will cost before confirming it.
- **Size: medium.** Split it: the reference refusal and the enumerated warning are small and use machinery that already exists; a real undo stack is a separate, larger job. Do the first two.

# TIER 1 — Wrong answers, confidently displayed

### 1.2 Query criteria are matched against raw stored base units

- **Guide:** WellView9UserGuide.1.062.html — "Value 1 and Value 2 must be in base units."
- **Now:** `wellviewDb.ts:2620-2628` pushes the typed string straight into `x."col" op ?`; only the isDate branch transforms anything. `/query-fields` returns `unit: mf?.baseUnit` (`:2194`) and `FieldPicker` renders `f.label` alone; `columnLabel` (`model.ts:146-167`) never appends a unit; the value box is free text over a DISTINCT-raw-values datalist. **The strongest single finding in the audit, and a one-line fix.**

- **Now:** `WellWindow.tsx:467` renders Print unconditionally; `:436-444` passes `html={html}`, which for a saved report is the literal `saved:<id>` set at `:224`. `PrintReport.tsx:90` calls `wvDbApi.templateDataPath(db, html, idwell, anchor)` **with no `saved:` branch** — unlike the viewer's own branches at `WellWindow.tsx:371` and `:405`. The request reaches `/template-data`, `templates().get("saved:<id>")` returns undefined (`wellviewSample.ts:419-420`), and `wellviewDb.ts:3196` sends `404 no template with html=saved:<id>` into `PrintReport.tsx`'s red error span.
- Fails for **every** saved report regardless of anchor. `e2e/tests/wellview-online.spec.ts:860-922` designs, saves, renders and edits one — and never presses Print.
- **Re-verified against the working tree: still live** (`grep "saved:" PrintReport.tsx` → nothing).
- **User cannot:** print anything they built. The feature looks complete until the last click.
- **Size: tiny** — one branch mirroring `WellWindow.tsx:371`, plus the e2e step that would have caught it.

- Formation gradients as a log track — `WellWindow.tsx:797-804` declines the whole track family rather than faking it; and no shipped template prints `wvJobWellboreGradient` either, so the desktop would print nothing from these templates.
- "Well Specific Other Elevation" datum — `datum.ts:76-90`: `wvElevationHistory` has zero rows in both databases, and "offering a datum that can only ever refuse would be worse than not offering it."
- The `wvWellbore` Directional Calculated Values — `calcFields.ts:11-45` states the refusal and why guessing would be worse; `calcFields.test.ts:75-80` pins it.
- Swab cumulative oil/BS&W/total — `calcFields.ts:358-368` names and refuses the self-table running-total shape by name.
- Export encryption — `transfer.ts:30`: "The wire format. Deliberately plain, so it can be read and diffed."

**Twenty-seven further claims were dismissed as not worth acting on**, the notable ones: spell check (browsers do it, with Ignore and Add-to-dictionary); "Show All Fields" vs "Show System Fields" (four fields total, two of them links into other Peloton products); per-field date/time format; the Between operator (the guide's *own* operator reference for the criteria builder lists exactly the app's ten); user profiles (the export ships no profile definitions at all); cement on tubing and annular fluids (0 rows in both databases); Group by Well in multi-well reports (no shipped `.afm` shown to be authored grouped); the schematic's zoom-region and right-click menu, loop-play delay, fonts and colours, and job selector; the templates-pane divider; F1/Ctrl+E/Ctrl+S; wireframe icons; the per-station `CalcOverride` gate (4 of 2,019 stations carry an override, and all 4 have the flag set, so output is byte-identical); the inventory source-job picker (no well in either database holds inventory on more than one job); Table Settings and the printed blank record; the Quick Query Clear button; and the depth/datum query warning — which was implemented anyway in `f048b52`, more strictly than the audit asked.

One code-hygiene item with no user consequence: `WellWindow.tsx:587-591` is unreachable — both `contentOnly` branches were added in the same commit (`e0055ec`), so the second has never executed.

The verification pass also corrected roughly thirty factual errors inside otherwise-correct claims — inflated counts (124 well-header columns → ~108 rendered; 12 nozzle templates → 9; 36 mis-drawn cement rows → 33; 218 tubing components → 182), misattributed citations, and two claims of absence that were false (`wvDepthAnnotation` *is* readable in Edit Data and *does* print in one template; `wvLogCurve` *does* exist with 19 rows). Those corrections are folded into the text above.

# What this audit could NOT determine

**1. Nothing was tested against a real WellView 9.0 installation.** Every finding rests on the vendor's decoded help text, the app's source, and two converted sample databases. Where the guide describes a behaviour without specifying its mechanism — the Time Log running total's reset rule, the perforation status partial-interval rule, whether the desktop gates survey overrides on `CalcOverride` — the desktop semantics are *inferred*, not known.

**2. Two databases, both samples.** Fourteen tables that findings touch have zero rows in both: `wvTimeCurve`, `wvJobOfflineTimeLog`, `wvElevationHistory`, `wvAnnularFluid`, `wvWorkingInt`/`wvWorkingIntLink`, `wvZoneLink`, all ten `wvLoc*`, and cement-on-tubing. "Zero rows in both" cannot distinguish *unused in these samples* from *unused in practice*. Record locking is the sharpest case: 0 of 44,608 rows locked, every `sysLockDateMaster` null — so an administrator integrity control is entirely untested and its real-world frequency unknown.

**3. The export is incomplete, and the missing pieces are exactly the specifications.** 23 `.sch` schematic templates, 31 `.afr` reports (182 of 213 present) and all six `.ttr` time-track templates are absent. What tracks a shipped schematic declares, which blocks a missing report holds, and what a Time Track even looks like cannot be established from this data.

**4. `reports.json` cannot tell a graph block from a text block from a schematic block.** `scripts/wellview-afr/afr_export.py` captured the length-prefix byte and dropped the string: the "Failure - Time Tracks" entry reads `misc_strings ["wvwellbore","(","%"]`, where `"("` is 0x28 = 40 = `len("Peloton.TimeTracks.GUI.TimeTracksControl")`. **33 templates embed an external control** (29 WellboreSchematic, 2 DaysVsDepth, 2 TimeTracks) and the JSON records none of them. Until the `.afr` export is re-run, the block-kind gap can be bounded but not measured — and no message the app shows can name the tool it is not reproducing.

**5. The `.afm` filter bytes are decoded but not disambiguated.** 5 of 57 multi-well templates carry operator tokens. For "Drill String Equipment with Query" the two fixed values sit beside a query reference, so whether they are hard-coded criteria or query-supplied values cannot be told from the bytes. The measured outcome (1,581 rows returned, 0 matching) holds either way.

**6. `wvLogCurve.CurveData` is an undecoded blob.** 18 curves carry data; the app renders `(binary · N bytes)`. Log tracks cannot be drawn, and LAS import cannot round-trip, until that format is decoded — which was not attempted here.

**7. Sync semantics cannot be recovered.** `Peloton.AppFrame.Sync.dll`'s `.psd` payload is compressed *and* encrypted, and `LastSync.mdb` is empty. What the desktop actually exchanges is unknown; only the fact that this app cannot merge is established.

**8. Tour sheet import cannot be specified from what ships.** The `.dll` and its `.ini` are present; no CAODC or IADC format description and no sample file exist in the repo. The `.ini` yields the time-log code mapping and carry-forward rules, and nothing about the file it reads.

**9. Two of the guide's three Simple Field Audit Rules have no data behind them.** The exported model carries `required` on 86 fields and `globalMetric` on 15, and has **no min/max attribute at all**. Whether Peloton stores those elsewhere or the export dropped them was not determined.

**10. Concurrency.** Eight files were modified in the working tree by another session while this was written. Findings were verified against HEAD, then re-verified against the working tree only for the datum family and the Tier 0 items. **Anything below Tier 2 should be re-checked against the tree before work starts.**

**11. The audit read code; it did not run the app.** The two hardest failures — the saved-report print 404 and the prompted-criterion empty result — were traced end to end through source and reproduced at the SQLite driver level, not in a browser. No click-through or screenshot evidence exists for any finding on this list.
