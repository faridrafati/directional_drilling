# Build a Directional Drilling Application — React + Node/SQLite

You are building a **modern web-based replacement** for a legacy Delphi (Borland Pascal) directional-drilling application called "MIXED." The original is a ~16,000-line desktop Win32 program with 27 forms; this rebuild must achieve **full feature parity** but as a clean, modern web app.

The reference Delphi source is available for algorithm fidelity, but you will NOT translate Pascal line-by-line. You are re-implementing the domain in idiomatic TypeScript with modern architecture.

---

## 1. Tech stack

**Frontend**
- React 18+ with TypeScript (strict mode)
- Vite as the build tool
- React Router for navigation
- Zustand for global state (light) + TanStack Query for server state
- Tailwind CSS + shadcn/ui for components
- TanStack Table for data grids (the survey editor needs an Excel-like grid)
- React Three Fiber + drei + Three.js for all 3D scenes
- Konva.js (or raw HTML5 Canvas) for 2D map / contour rendering
- D3 (or visx) for 2D charts (cross-sections, plan view, vertical section)
- react-hook-form + zod for forms/validation
- pdfmake or @react-pdf/renderer for report PDF output
- SheetJS (xlsx) for Excel export

**Backend**
- Node 20+ with TypeScript
- Fastify (preferred) or Express
- Prisma ORM + SQLite (single-file DB; equivalent to the original `.mdb`)
- Zod for request validation; share schemas with the frontend
- REST API (OpenAPI spec autogenerated)
- File-based "project" model: each project is one SQLite file the user can save/load/export

**Project layout (monorepo)**
```
/apps
  /web         React frontend
  /api         Fastify backend
/packages
  /shared      Types, zod schemas, unit conversions, trajectory math

/prisma        schema.prisma + migrations
```

The trajectory math and unit conversions **must live in `/packages/shared`** so both UI (live preview) and API (batch calc) use the same code. No duplication.

## 2. Domain glossary (for non-drilling readers)

| Term | Meaning |
|---|---|
| **MD** | Measured Depth — total length along the wellbore (ft or m) |
| **TVD** | True Vertical Depth — straight-down depth |
| **INC** (inclination) | Angle from vertical, 0°=straight down, 90°=horizontal |
| **AZM** (azimuth) | Compass heading of wellbore, 0°=North, 90°=East |
| **NS / EW** | North-South and East-West offset from surface location |
| **VSEC** | Vertical Section — projection of well path onto a chosen azimuth plane |
| **DLS** | Dogleg Severity — change in trajectory per 100 ft/30 m |
| **TF** | Toolface — angular orientation of bent sub |
| **BR / TR** | Build Rate / Turn Rate — rate of inclination / azimuth change |
| **DMD** | Delta MD between two consecutive survey stations |
| **KOP** | Kick-Off Point — depth where well starts deviating |
| **EOC** | End of Curve |
| **Survey Station** | One sampled point on the wellbore (MD, INC, AZM, …) |
| **Target** | Bottom-hole geological target the well must reach |

## 3. Data model

A **Project** is the top-level container (one SQLite file). Inside a project:

```
Country (1) ──< Field (1) ──< Well (1) ──< Calculation (1) ──< Survey
                                              ▲
                                              │
                                       (type: "WellDesign" | "SurveyEditor")
```

Prisma schema (essentials):

```prisma
model Project {
  id        String    @id @default(cuid())
  name      String
  units     Units     // see §4
  createdAt DateTime  @default(now())
  countries Country[]
}

model Country {
  id        String  @id @default(cuid())
  projectId String
  name      String
  area      String?
  project   Project @relation(fields: [projectId], references: [id], onDelete: Cascade)
  fields    Field[]
}

model Field {
  id        String  @id @default(cuid())
  countryId String
  name      String
  ns        Float?  // surface NS coordinate
  ew        Float?
  msl       Float?  // mean sea level / KB elevation
  country   Country @relation(fields: [countryId], references: [id], onDelete: Cascade)
  wells     Well[]
  grids     GridFile[]  // .grd files attached to the field
}

model Well {
  id           String        @id @default(cuid())
  fieldId      String
  name         String
  ns           Float?
  ew           Float?
  msl          Float?
  wellType     String?       // "vertical", "directional", etc.
  tvd          Float?
  md           Float?
  comment      String?
  field        Field         @relation(fields: [fieldId], references: [id], onDelete: Cascade)
  calculations Calculation[]
}

model Calculation {
  id        String          @id @default(cuid())
  wellId    String
  name      String
  type      CalculationType // WellDesign | SurveyEditor
  well      Well            @relation(fields: [wellId], references: [id], onDelete: Cascade)
  segments  Segment[]       // input rows (the design intent)
  stations  Station[]       // calculated survey at 100ft/30m intervals
}

model Segment {
  id              String      @id @default(cuid())
  calculationId   String
  order           Int         // sequence within the calculation
  profileType     Int         // see §6 — codes 1-103
  comment         String?
  md              Float
  inc             Float       // radians internally; degrees on the UI
  azm             Float
  tvd             Float
  vsec            Float
  ns              Float
  ew              Float
  dls             Float
  tf              Float
  br              Float
  tr              Float
  dmd             Float
  surveyTools     String?
  calculation     Calculation @relation(fields: [calculationId], references: [id], onDelete: Cascade)
}

model Station {
  id            String      @id @default(cuid())
  calculationId String
  order         Int
  comment       String?
  md            Float
  inc           Float
  azm           Float
  tvd           Float
  vsec          Float
  ns            Float
  ew            Float
  dls           Float
  tf            Float
  br            Float
  tr            Float
  dmd           Float
  calculation   Calculation @relation(fields: [calculationId], references: [id], onDelete: Cascade)
}

model GridFile {
  id        String @id @default(cuid())
  fieldId   String
  name      String
  filename  String
  // parsed metadata:
  xmin      Float
  xmax      Float
  ymin      Float
  ymax      Float
  xinc      Float
  yinc      Float
  ncol      Int
  nrow      Int
  units     String   // "m" | "km" | "ft" | "yd" | "ml" | "nm"
  errorVal  Float    // sentinel (commonly 1e30)
  data      Bytes    // float32[ncol*nrow] little-endian; nulls = errorVal
  field     Field    @relation(fields: [fieldId], references: [id], onDelete: Cascade)
}

enum CalculationType { WellDesign  SurveyEditor }
```

**Storage rule:** all angles stored in **radians**, all distances in the project's chosen unit. Convert only at the UI boundary.

## 4. Unit system

The original supports 9 unit profiles (per `Unit42.pas`). Reproduce:

```ts
type LengthUnit = "cm" | "m" | "km" | "ft" | "yd" | "mi" | "nmi";
type AngleUnit  = "deg" | "rad";
type DLSUnit    = "deg/100ft" | "deg/30m";

interface UnitSystem {
  length: LengthUnit;
  angle: AngleUnit;     // input only; storage is radians
  dls: DLSUnit;
  // 9 presets: API, Metric, US, Imperial, plus mixed variants
}
```

Conversion factors (from `Unit23.pas` — verify against original):
```
cm:  base
m:   ×100 cm
km:  ×1000 m
ft:  1 m = 3.2808398950 ft
yd:  1 m = 1.0936132983 yd
mi:  1 m = 6.213712e-4 mi
nmi: 1 m = 5.399568e-4 nmi
```

Provide one canonical `convert(value, fromUnit, toUnit)` function in `/packages/shared`.

## 7. `.grd` file format

The original reads Schlumberger / Landmark ASCII grid files (`.grd`). See `old_delphi_code/NEW FIELD/TOP_HITH_DEPTH.grd` for a real example.

Format (port from `Unit21.pas:FieldExtract`):

```
FSASCI 0 1 "<error_value>" 0 <max_value> 0
FSATTR 0 0
!Grid Lattice: ...
!VOI Box           XMIN: <num> <unit>
!                  XMAX: <num> <unit>
!                  YMIN: <num> <unit>
!                  YMAX: <num> <unit>
!Lattice           XINC: <num> <unit>
!                  YINC: <num> <unit>
!                  NCOL: <int>
!                  NROW: <int>
... (other ! header lines ignored)
<blank line>
<data block: NCOL × NROW floats, whitespace-separated, line-wrapped>
```

- The "error" sentinel (commonly `1.0e30`) marks no-data cells; preserve as `NaN` internally and re-emit on export
- Implement both `parse()` and `serialize()` in `/packages/grd`
- Auto-detect units from the line containing `XMIN:` (`m`, `km`, `ft`, `yd`, `ml`, `nm`)
- Unit tests with the included `TOP_HITH_DEPTH.grd` (469 × 615 50m grid in Lambert Conformal Conic)

## 8. UI/UX guidelines

- **Layout:** persistent left sidebar (tree explorer) + main work area + optional right inspector panel
- **Look:** clean light theme with shadcn/ui defaults; no skeuomorphism (the original looks like Windows XP — modernize)
- **Grid interactions:** keyboard navigation (arrows, tab, enter); cut/copy/paste from Excel; multi-cell selection
- **All angles displayed in degrees** (with the project's degree symbol formatting); user input parses both `12.5` and `12° 30'`
- **All depths in the project's length unit;** display the unit suffix
- **Numeric input precision:** 3 decimals for distances, 2 for angles, mirror the original `dec(3, ...)` and `dec(2, ...)` calls
- **Undo/redo** for grid edits (Cmd-Z / Ctrl-Z); use a command pattern
- **Auto-save** the active project every 30 s to the backend (debounced)
- **Loading states**: trajectory recalc on >50 segments may take a moment — show spinner; don't block the UI
